## 项目级计划模式核心约束

仅当当前项目 `.planning/active.json` 存在且 `mode=active` 时执行本区块；上下文压缩后先恢复这些规则，再继续工作。强制加载全局规范的时机：仅在开始一份完整计划之前（新建计划或为当前会话开启新需求）先完整读取 `~/.agents/skills/common-guide/SKILL.md`，未加载前不得开始需求分析与建计划；恢复已有计划、讨论推进与实施轮次不重复强制。本区块常驻在全局 `AGENTS.md`（pi 为 `~/.pi/agent/AGENTS.md`），对所有项目加载；当前项目不满足条件时**完全忽略本区块**：不读取计划文件、不声明计划模式、不执行其中任何门禁。

1. 每轮开始先读取 `.planning/active.json` 与当前需求的 `index.md`，确认当前步骤、计划状态、责任边界、实施批次和未决讨论点；回复首行声明 `📋 计划模式 · <需求> · 当前步骤 Sxx · 未决讨论点 N 个`。
2. 只实施同时满足以下条件的步骤：责任为“我负责”、处于本次明确授权范围内、状态为`🟢 可实施`或该授权下的`🚧 实施中`，且第 8 条的讨论点门禁已通过。他人负责的工作只能登记为外部依赖、输入、协作事项或待确认项。实施命令已经生效后，任一条件不满足的步骤登记阻塞并继续其它已满足条件的步骤，不为该步骤停下来提问。
3. 一个步骤可以拆成多个实施批次。批次使用稳定的 B01、B02…编号；批次完成不等于步骤完成：批次完成后步骤保持`🚧 实施中`，所有批次完成且本步骤测试基线全部为`✅ 有效`或登记为`⏸ 未验证`并写明原因后才变为`✅ 已完成`。实施命令已经生效时，该验收以各批次流程测试和自行核对为准，不等待用户当场回复。
4. 每个实施批次的代码落地后、标记完成前，必须先按该批次验收条件实际测试一遍，走通本次改动的主流程和关键交互，确认流程与交互通畅。测试失败先修复再测，不得未测就收尾。结果写入步骤“产出”、步骤「测试基线」台账和 Review 自测；环境或权限导致无法执行时列入未验证项并写明原因。
   - 每个步骤维护「测试基线」表（V 编号，表头 `| 编号 | 覆盖项 | 类型 | 验证方式 | 锚点 | 状态 | 最近通过 |`）。状态取 `✅ 有效`（已通过且未受后续改动影响，可直接引用）、`♻️ 待复测`、`❌ 失效`、`⏸ 未验证`；通过项记录最近通过的批次，Review 自测直接引用 V 编号，禁止每次从零重列。
   - 新增批次按影响面选测，不默认全量重测，也不得以“只测改动点”跳过错共享依赖：只改样式值只复测视觉项，只改文案只复测展示项；改组件逻辑或字段读写，复测该组件功能项与所有消费该字段的页面项；改公共组件、composable、store、请求函数或共享类型，全部使用处的相关项失效。选测依据写入 Review「增量复测」，未复测项逐条写明“不相关判定”或“风险接受”。
   - 步骤收尾（Sxx 转 `✅`）、公共代码改动、跨页面结构变更、提测或发布前，仍跑该步骤完整基线，防止台账长期漂移。
   **测试之后必须执行收尾（与上面的基线维护并列执行）：**
   - 更新批次状态、步骤状态、`index.md`、步骤片段和 `active.json`；
   - 文档版本 +1，记录修改文件、验证结果、未验证项和提交状态；
   - 生成 `review/Sxx-Bxx-review.md`。Review 按改动分级，避免样式值微调也写全套模板：
     - **L1 轻量模板**：仅样式值/文案/类名微调，不改组件结构、逻辑、Props 与接口的批次，只写五节——`需求意图/锚点`、`修改文件总览`、`自测`、`增量复测`、`未复测项`，10～20 行即可；不强制脉络图、接口变更清单与代码结构清单。
     - **L2 全模板**：功能逻辑、代码结构、接口、新页面批次以及步骤收尾，适用以下全部小节：
       - 必须先放一张 `页面与组件脉络图`（使用 mermaid flowchart，展示页面结构、组件层级与数据/事件流向），再放需求意图/锚点、修改文件总览、风险、自测、未验证项和建议审查顺序；图中关键节点可用 Mermaid `click` 指向对应的 Review 细节。
       - 必须包含 `增量复测`：本次改动点 → 受影响 V 项（复用 / 失效）→ 实际复测结果；以及 `未复测项`：每个未复测 V 项写明不相关判定或风险接受，不得留空。
       - 必须包含 `接口变更清单`：记录新增、修改、删除/废弃接口，以及需求涉及但保持原契约的复用接口；修改接口必须写请求/响应字段前后变化、兼容性和前端动作；无变化时明确写“无接口变化”。
       - 必须包含 `代码结构与调用清单`：说明实际涉及的页面/组件/composable/store/请求函数、职责、调用入口与时机、Props/参数/返回值、内部流程、状态/副作用/边界和设计与实际差异；无结构变化时明确写“本批次无代码结构变更”。
   - 涉及视觉的批次（含 L1）仍必须包含 `界面还原对照`：按页面并列设计资源（D 编号/链接/图片）与实现截图，逐项核对布局骨架、栅格间距、字号字重、颜色、圆角、图标、交互态和响应式断点，写明差异、原因及是否经用户确认；纯样式值微调可用 computed 断言替代整页截图。
   - `/plan-build` 在步骤收尾、提测节点或用户要求时执行，交付“先总览、再接口对接和代码理解、再文件细节”的 Review 入口；单批次收尾只写步骤片段、`active.json` 和文档版本，不逐批重建 HTML。
5. 每次写回计划源文件后完成三同步：写回受影响片段，更新 `active.json`，重建计划 HTML。`active.json`、`index.md` 元信息、步骤总表状态和步骤标题状态必须一致；`active.json` 只保留当前需求的一套元信息与键名体系，禁止两套需求字段、两个版本号或中英文键并存；发现混杂时先归档清理旧字段、统一版本号再同步。计划源文件是唯一真相，`build/plan.html` 是生成物，不手工修改；单纯构建不增加文档版本。只有实际读取并核对文件、且构建成功后，才能在回复中声明同步完成。
6. 讨论阶段每轮只推进 1～3 个相关讨论点；需求口径、责任分工、Forum 已确认决策冲突时不得自行选择，必须登记冲突并向用户或责任方确认。这条条数限制只约束讨论，不约束第 9 条的逐条改 Bug。
7. 如果无法确认当前状态，先读取 `active.json`、`index.md`、当前步骤的“实施批次”“责任与协作”“界面设计基线”“产出”和最近 Review 文件；禁止凭记忆继续编码。发现 active/index/步骤标题冲突时，先报告冲突并停止状态推进，不得用回复文字代替计划文件写回。
8. 每个新步骤或历史步骤新增批次进入实施前，`待讨论点`必须全部处于已确定、不适用、已下分或已废止状态；未决项不得通过回复文字绕过门禁。接口设计只覆盖前端调用的后端 HTTP 接口，不覆盖后端内部实现（Service/Repository/Mapper/跨服务调用/消息事件）；普通查询接口不单独审查。代码结构发生新增、删除、拆分、合并、组件 Props/Emits/状态流向/依赖/调用链/响应式状态/副作用变化时，必须把相关页面/组件/composable/store/请求函数纳入`待讨论点`逐项讨论；没有结构变化时明确登记不适用。历史已完成步骤按新旧兼容规则处理。

9. 命令「开始改“XXX”bug」/「继续改“XXX”bug」/「修改“XXX”bug」按下面执行：
   - 没有指明具体 Bug、也没有给出链接时，直接打开 `https://task.ukeping.com/my-work-bug-assignedTo.html`，读完测试人员登记并指派给当前用户的 Bug 列表（含分页）。只处理标题包含 XXX、且状态为「已激活」的条目。XXX 为 figma 时（不区分大小写），命中条目按 Bug ID 数值从小到大逐条修改，不按列表展示顺序；其它关键字仍按列表顺序逐条修改。列表中的「激活」与「已激活」同一处理。「已解决」以及其它非已激活状态跳过，不修改、不测试、不记录。已经给出具体 Bug 或链接时，先核对状态，只改状态为「已激活」的那一条。
   - 页面需要登录时使用当前已登录会话。会话失效、列表读不到或没有标题命中时停止并说明，不凭记忆修改。
   - 该命令就是全部命中条目的实施授权，不是只授权前 1～2 条。逐条修改的全过程中，确认与授权直接通过，不再停下来问，包括方案取舍、是否继续、是否允许修改。按既定顺序逐条打开详情并修改。不扩大到未命中条目，也不改他人的 Bug，也不执行用户未明确要求的 git commit / push。
   - 需要后端提供字段或修改接口才能修复的 Bug，前端不能自行处理。在 Review 或 Bug 记录中单独标为「待后端」，写明 Bug 编号（带禅道链接）/标题、接口方法与路径、需要新增或修改的字段、以及前端无法单独修复的原因。不补假字段、不改后端实现、不把该条记为已修复。标记后继续下一条。
   - 本命令不受第 6 条「每轮 1～3 个」限制。命中的已激活条目必须在同一次执行里按既定顺序全部走完「修改 → 测试 → 记录」，禁止改完 1 条或 2 条就结束回复、做阶段性汇报或等待下一次口头命令。单条 Review、三同步和 `/plan-build` 只是该条的记录动作，写完立即进入下一条，不把交付 Review 当作本轮结束。测试须按该 Bug 的复现步骤执行，确认现象消失且相关流程、交互通畅；测试失败先修再测。单条因环境或权限无法测试时列入未验证项并写明原因，然后继续下一条；不得以条目数量、回复篇幅或需要用户确认作为停止理由。只有命中条目都已处理（含标为「待后端」、未验证或按状态跳过）后，才一次性汇报。若执行被上下文或会话中断，汇报必须列出已完成 ID 和尚未处理的 ID。
   - 调整代码结构时，先在`待讨论点`补充代码结构设计项并完成理解确认，再修改代码。本命令已经生效时，理解确认改为对照 Bug 详情与代码自行核对并写回，不停下来提问。只修正局部逻辑、不改变结构时，不强制新增结构设计点，但仍要更新受影响函数的行为理解。
   - 每条完成后把现象→入口→页面/组件/函数→根因→修复→测试链路写入 Review 或 Bug 记录，并检索同模式点。同模式且属于该 Bug 的一并修正；跨出本次命中范围的只登记。
   - 记录禅道来源的 Bug 时，编号一律写成可点击的 Markdown 链接：`[#<id>](https://task.ukeping.com/bug-view-<id>.html)`，例如 `[#12345](https://task.ukeping.com/bug-view-12345.html)`。Review、Bug 记录、「待后端」清单和最终汇报中列出的 ID 都按此格式，方便直接跳转查看详情；非禅道来源的编号不加此链接。
10. 涉及前端视觉的改动以 UI 设计图/设计链接为唯一视觉验收基线，优先级高于既有代码样式和组件库默认样式：设计资源必须登记在 `index.md` 设计资源表（D 编号起）与步骤`界面设计基线`中；写样式代码前必须实际打开设计资源，把该页面相关帧的**全部标注值（背景/边框/圆角/阴影/内边距/字号字重/间距/交互态）一次性量取为规格表**登记进步骤片段，禁止每轮只量当前反馈点、逐属性返工；实施按规格表逐项打钩。用户截图反馈先对照规格表归类：表内偏差直接修，表外缺失项补登记进规格表；**一次反馈中的多个差异点合并为一个批次实施**，禁止逐点开批。样式修复前先核对完整布局链（父级 flex/align 对齐、组件库自动附加的全局类、`:deep` 穿透与 CSS 变量覆盖边界）定位真根因再改；同一区域第二轮修复前必须先说明首轮根因为何未找准。资源不可访问、缺失或未覆盖的状态必须登记阻塞，不得自行发挥；讨论阶段向用户索要，实施命令已经生效时跳过该部分并继续其它已满足条件的工作，不原地等待。`待讨论点`中视觉对照项未全部确认的视觉步骤不得进入实施。
11. 用户一旦发出开始实施的命令，本次实施过程中的确认与授权直接通过，不再停下来问，包括夜间或用户不在场。方案取舍采用计划里已确认的结论或已写明的推荐方案；理解验收改为对照已确认计划与本批次测试结果自行核对并写入 Review，不要求用户当场复述。连续执行到本次授权范围结束，再一次性汇报。不得借此越过授权范围、实施他人负责的工作，或在用户未明确要求时执行 git commit / push。与已确认计划冲突且计划中没有可执行结论的事项，只登记阻塞并跳过，不猜测，也不等待回复。
12. 计划视图默认用 Orca 浏览器打开：当前会话在 Orca 工作区（存在 `ORCA_TERMINAL_HANDLE`、`ORCA_WORKTREE_ID`，且 `orca-cli-safe status --json` 显示 app.running=true、runtime.state=ready）时，构建完 `build/plan.html` 后用 Orca 内嵌浏览器打开或复核，不回退到系统默认浏览器。打开方式：`orca-cli-safe tab list --json` 查现有标签；没有可用标签时 `tab create --json`；再 `goto --url file://<绝对路径> --json`，路径含中文等非 ASCII 字符时先做 URL 编码。同一需求已有计划标签时优先切换并让用户原生刷新，不重复开新标签。非 Orca 环境仍用 `open`（macOS）或 `xdg-open`（Linux）。
13. 提测终态与反馈通道：执行提测动作时，所有“我负责”的`🚧 实施中`步骤转为`✅ 已完成（已提测）`，`active.json`、`index.md` 步骤总表和步骤标题三处一致，后续不再对该需求新增实施批次编号。提测后的用户反馈登记到 `index.md` 的「提测反馈记录」：每条含日期、现象/复现步骤、根因、修复、验证结果和增量复测的 V 项；同一反馈中的多个差异点合并为一条记录、一个修复动作（可挂最后完成的步骤或独立 F 编号），禅道来源的反馈按第 9 条链接格式写编号；完成后更新测试基线并递增文档版本，不再走 B 批次与 L2 全模板。与第 9 条禅道 Bug 命令互不影响：已登记为禅道 Bug 的反馈走第 9 条通道。
14. 联调前置检查：端到端联调类步骤进入实施前，先验证测试账号、造数脚本、后端部署版本与真实响应可用；不可用时登记阻塞并继续其它已满足条件的工作，不在联调中途现场造数或原地等待。测试账号、造数脚本、部署版本作为外部依赖登记在 `index.md`。后端口径落地部署后以实测响应回填类型与枚举（口径帖/文档仅作参考，通用规则见全局约束第 18 条），并向接口方输出关键闭环验收场景清单（如 退回→重交→重评→重公布），闭环缺陷由接口方在自测阶段覆盖，不留给前端联调发现。

核心提示词以受管控区块（`<!-- PLAN-MODE:BEGIN/END -->`）写入**全局** `AGENTS.md`（pi 为 `~/.pi/agent/AGENTS.md`，可用 `PI_CODING_AGENT_DIR` 覆盖），不再写入项目 `AGENTS.md`，避免提示词随业务仓库提交。写入命令为 `node ~/.agents/skills/plan-start/scripts/plan-mode.mjs install`；调整本文件后执行同一脚本的 `sync` 子命令，自检通过后再重新加载上下文（pi 用 `/reload`，其它环境重开会话或重新加载上下文）。历史项目内残留的区块用 `remove --project` 清理；移除全局区块用 `remove`。
