## 项目级计划模式核心约束

仅当 `.planning/active.json` 存在且 `mode=active` 时执行本区块；上下文压缩后先恢复这些规则，再继续工作：

1. 每轮开始先读取 `.planning/active.json` 与当前需求的 `index.md`，确认当前步骤、计划状态、责任边界、实施批次和未决讨论点；回复首行声明 `📋 计划模式 · <需求> · 当前步骤 Sxx · 未决讨论点 N 个`。
2. 只实施同时满足以下条件的步骤：责任为“我负责”、处于本次明确授权范围内、状态为`🟢 可实施`或该授权下的`🚧 实施中`，且第 8 条的讨论点门禁已通过。他人负责的工作只能登记为外部依赖、输入、协作事项或待确认项。实施命令已经生效后，任一条件不满足的步骤登记阻塞并继续其它已满足条件的步骤，不为该步骤停下来提问。
3. 一个步骤可以拆成多个实施批次。批次使用稳定的 B01、B02…编号；批次完成不等于步骤完成：批次完成后步骤保持`🚧 实施中`，所有批次完成且本步骤验证通过后才变为`✅ 已完成`。实施命令已经生效时，该验收以各批次流程测试和自行核对为准，不等待用户当场回复。
4. 每个实施批次的代码落地后、标记完成前，必须先按该批次验收条件实际测试一遍，走通本次改动的主流程和关键交互，确认流程与交互通畅。测试失败先修复再测，不得未测就收尾。结果写入步骤“产出”和 Review 自测；环境或权限导致无法执行时列入未验证项并写明原因。测试之后必须执行收尾：
   - 更新批次状态、步骤状态、`index.md`、步骤片段和 `active.json`；
   - 文档版本 +1，记录修改文件、验证结果、未验证项和提交状态；
   - 生成 `review/Sxx-Bxx-review.md`；
   - Review 必须先放一张 `页面与组件脉络图`（使用 mermaid flowchart，展示页面结构、组件层级与数据/事件流向），再放需求意图/锚点、修改文件总览、风险、自测、未验证项和建议审查顺序；图中关键节点可用 Mermaid `click` 指向对应的 Review 细节。
   - Review 必须包含 `接口变更清单`：记录新增、修改、删除/废弃接口，以及需求涉及但保持原契约的复用接口；修改接口必须写请求/响应字段前后变化、兼容性和前端动作；无变化时明确写“无接口变化”。
   - Review 必须包含 `代码结构与调用清单`：说明实际涉及的页面/组件/composable/store/请求函数、职责、调用入口与时机、Props/参数/返回值、内部流程、状态/副作用/边界和设计与实际差异；无结构变化时明确写“本批次无代码结构变更”。
   - 涉及视觉的批次 Review 必须包含 `界面还原对照`：按页面并列设计资源（D 编号/链接/图片）与实现截图，逐项核对布局骨架、栅格间距、字号字重、颜色、圆角、图标、交互态和响应式断点，写明差异、原因及是否经用户确认。
   - 执行 `/plan-build`，交付“先总览、再接口对接和代码理解、再文件细节”的 Review 入口。
5. 每次写回计划源文件后完成三同步：写回受影响片段，更新 `active.json`，重建计划 HTML。`active.json`、`index.md` 元信息、步骤总表状态和步骤标题状态必须一致；计划源文件是唯一真相，`build/plan.html` 是生成物，不手工修改；单纯构建不增加文档版本。只有实际读取并核对文件、且构建成功后，才能在回复中声明同步完成。
6. 讨论阶段每轮只推进 1～3 个相关讨论点；需求口径、责任分工、Forum 已确认决策冲突时不得自行选择，必须登记冲突并向用户或责任方确认。
7. 如果无法确认当前状态，先读取 `active.json`、`index.md`、当前步骤的“实施批次”“责任与协作”“界面设计基线”“产出”和最近 Review 文件；禁止凭记忆继续编码。发现 active/index/步骤标题冲突时，先报告冲突并停止状态推进，不得用回复文字代替计划文件写回。
8. 每个新步骤或历史步骤新增批次进入实施前，`待讨论点`（包括其子项`待讨论接口设计`、`待讨论代码设计`和`待讨论界面设计`）必须全部处于已确认、不适用、已下分或已废止状态；未决项不得通过回复文字绕过门禁。接口设计只覆盖前端调用的后端 HTTP 接口，不覆盖后端内部实现（Service/Repository/Mapper/跨服务调用/消息事件）；普通查询接口不单独审查。代码结构发生新增、删除、拆分、合并、组件 Props/Emits/状态流向/依赖/调用链/响应式状态/副作用变化时，必须把相关页面/组件/composable/store/请求函数纳入代码设计讨论；没有结构变化时明确登记不适用。历史已完成步骤按新旧兼容规则处理。

9. 命令「开始改XXX bug」按下面执行：
   - 没有指明具体 Bug、也没有给出链接时，直接打开 `https://task.ukeping.com/my-work-bug-assignedTo.html`，读完测试人员登记并指派给当前用户的 Bug 列表（含分页），只处理标题包含 XXX 的条目，按列表顺序逐条修改。已经给出具体 Bug 或链接时，只改该条。
   - 页面需要登录时使用当前已登录会话。会话失效、列表读不到或没有标题命中时停止并说明，不凭记忆修改。
   - 该命令就是命中条目的实施授权。先打开该条详情，再按复现步骤修改。不扩大到未命中条目，也不改他人的 Bug。
   - 每改完一条，必须先按该 Bug 的复现步骤测试，确认现象消失且相关流程、交互通畅，再写下一条。测试失败先修再测。环境或权限无法执行时列入未验证项并写明原因，不得未测就当作完成。
   - 调整代码结构时，先补充`待讨论代码设计`并完成理解确认，再修改代码。本命令已经生效时，理解确认改为对照 Bug 详情与代码自行核对并写回，不停下来提问。只修正局部逻辑、不改变结构时，不强制新增结构设计点，但仍要更新受影响函数的行为理解。
   - 每条完成后把现象→入口→页面/组件/函数→根因→修复→测试链路写入 Review 或 Bug 记录，并检索同模式点。同模式且属于该 Bug 的一并修正；跨出本次命中范围的只登记。
10. 涉及前端视觉的改动以 UI 设计图/设计链接为唯一视觉验收基线，优先级高于既有代码样式和组件库默认样式：设计资源必须登记在 `index.md` 设计资源表（D 编号起）与步骤`界面设计基线`中；写样式代码前必须实际打开设计资源逐项对照，禁止凭记忆或“看起来差不多”还原；资源不可访问、缺失或未覆盖的状态必须登记阻塞，不得自行发挥；讨论阶段向用户索要，实施命令已经生效时跳过该部分并继续其它已满足条件的工作，不原地等待。`待讨论界面设计`未全部确认的视觉步骤不得进入实施。
11. 用户一旦发出开始实施的命令，本次实施过程中的确认与授权直接通过，不再停下来问，包括夜间或用户不在场。方案取舍采用计划里已确认的结论或已写明的推荐方案；理解验收改为对照已确认计划与本批次测试结果自行核对并写入 Review，不要求用户当场复述。连续执行到本次授权范围结束，再一次性汇报。不得借此越过授权范围、实施他人负责的工作，或在用户未明确要求时执行 git commit / push。与已确认计划冲突且计划中没有可执行结论的事项，只登记阻塞并跳过，不猜测，也不等待回复。

核心提示词由计划模式入口注入项目 `AGENTS.md` 的受管控区块（`node ~/.agents/skills/plan-start/scripts/plan-mode.mjs install`）；调整本文件后执行同一脚本的 `sync` 子命令，自检通过后再重新加载上下文（pi 用 `/reload`，其它环境重开会话或重新加载上下文）。
